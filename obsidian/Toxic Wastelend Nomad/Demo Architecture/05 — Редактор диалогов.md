# Выбор редактора диалогов

Статус: рекомендация для проверки прототипом; сторонний плагин пока не выбран окончательно и не установлен.

## Требования проекта

Редактор должен поддерживать:

- большой объём текста;
- независимые персональные диалоги NPC;
- условия появления сообщений на основе состояния мира;
- варианты ответа и сходящиеся ветки;
- принятие, отказ, продвижение и сдачу квестов;
- вызов специальных сообщений: торговля и улучшения;
- постоянные идентификаторы строк и узлов;
- локализацию;
- проверку ошибок и потерянных переходов;
- собственный интерфейс мессенджера вместо навязанного диалогового окна;
- GDScript и Web/HTML5.

## Рекомендуемый вариант: Dialogue Manager

Dialogue Manager следует использовать как язык и редактор сценариев, но не как готовый экран диалога.

Он подходит проекту по следующим причинам:

- работает внутри Godot;
- предназначен для ветвящихся диалогов;
- поддерживает условия и изменения состояния;
- имеет проверку синтаксиса;
- поддерживает локализацию;
- его runtime не владеет состоянием игры: источником истины остаётся архитектура проекта;
- стандартное диалоговое окно можно не использовать, подключив собственное представление.

Разделение ответственности:

```text
Dialogue Manager
  текст → условия → варианты → переходы → команды

Система ХАБа проекта
  контакты → сообщения → журнал → торговля → улучшения → сохранение
```

Специальные действия диалога должны передавать системе ХАБа команду с идентификатором, например:

```text
предложить квест water_fragments
открыть торговлю mechanic_store
открыть улучшения workshop_robot
открыть точку карты old_pump_station
```

Диалог не должен напрямую менять интерфейс, инвентарь или карту. Он только формулирует намерение; соответствующая игровая система проверяет и выполняет его.

## Dialogic 2

Dialogic предлагает визуальные и текстовые таймлайны, персонажей, условия, сигналы, локализацию и расширяемые пользовательские события.

Плюсы:

- удобный визуальный редактор событий;
- готовая работа с персонажами и портретами;
- можно добавить собственные события торговли, квеста и улучшения;
- можно создать собственный layout.

Минусы для этого проекта:

- ориентирован прежде всего на последовательное воспроизведение диалога и visual novel;
- значительная часть встроенных систем пересекается с уже определённой моделью ХАБа;
- интеграция персональных асинхронных чатов и постоянного журнала потребует глубокой адаптации;
- Dialogic 2 официально всё ещё помечен как alpha, поэтому возможны изменения рабочего процесса.

Dialogic стоит выбирать, если визуальное редактирование важнее простоты интеграции и команда готова принять его модель таймлайнов как основу.

## Yarn Spinner

Yarn Spinner имеет сильный язык сценариев, графовое представление и инструменты для писателей. Однако его GDScript-интеграция для Godot пока находится в alpha и сама документация не рекомендует её для выпуска игры. Рекомендуемая C#-версия не подходит для Web-экспорта Godot 4.

Для текущего демо этот вариант следует отложить.

## Собственный редактор

Полный визуальный редактор с нуля сейчас не рекомендуется. Он потребует создать и сопровождать:

- графический canvas;
- узлы и соединения;
- сериализацию и миграции формата;
- undo/redo;
- копирование и вставку;
- поиск и навигацию;
- проверку условий и переходов;
- поиск использования переменных и квестов;
- локализацию;
- тестовый проигрыватель;
- восстановление после повреждённых данных.

Это самостоятельный инструментальный проект, который может начать конкурировать по объёму с механикой самого ХАБа.

## Когда свой редактор оправдан

Собственный редактор становится разумным, если после реального прототипа выяснится, что готовый инструмент не выражает ключевую модель проекта:

- асинхронные сообщения от нескольких NPC;
- специальные карточки внутри истории;
- повторное открытие старых диалогов;
- сложное планирование сообщений по состоянию мира;
- обзор связей между фракциями и квестами.

В таком случае сначала сохраняется собственная модель данных и runtime, а затем над ней строится узкий редактор. Начинать следует не с универсального графа, а с необходимых проекту экранов:

1. список NPC и эпизодов;
2. редактор последовательности сообщений;
3. ветки ответов;
4. условия и последствия из ограниченного каталога;
5. проверка ссылок;
6. предпросмотр диалога.

## Предлагаемый путь

1. Проверить Dialogue Manager на одном законченном эпизоде.
2. Эпизод должен включать обычный текст, развилку, предложение квеста, повторный вход после полёта и сдачу квеста.
3. Вывести результат через собственный интерфейс мессенджера.
4. Встроить одну торговую карточку как специальную команду.
5. Проверить восстановление истории после сохранения и Web-экспорт.
6. Только после этого решить, достаточно ли готового редактора или нужен собственный.

## Предварительное решение

Для демо: Dialogue Manager как авторский язык и парсер плюс собственные runtime, журнал и UI ХАБа.

Собственный полноценный визуальный редактор: не делать до проверки одного вертикального сценарного эпизода.
