# Хранение данных

Статус: рекомендуемая архитектура для Godot 4.7 с поддержкой desktop и Web/HTML5.

## Решение

Данные разделяются на два слоя:

```text
Авторский контент в res:// + состояние прохождения в user://
```

Для демо продолжительностью 45–60 минут отдельная база данных не требуется.

## 1. Авторский контент

Контент поставляется вместе с игрой, доступен только для чтения и хранится в `res://`.

Рекомендуемый основной формат — типизированные Godot Resource-файлы (`.tres`):

- контакты NPC и ссылки на аватары;
- определения сообщений;
- варианты ответов;
- запросы и квесты;
- каталог товаров;
- определения пассивных перков;
- известные точки карты;
- условия появления сообщений;
- последствия выбора.

Каждая сущность получает постоянный строковый идентификатор. Сохранение ссылается на контент по этим идентификаторам и не копирует в себя весь авторский текст.

Тексты сообщений желательно хранить через ключи локализации. Это позволяет менять перевод и оформление, не ломая старое сохранение.

JSON или CSV допустимы как внешний авторский формат, если контент удобнее готовить таблицами. Внутри игры они не должны становиться вторым параллельным источником истины: перед сборкой данные приводятся к одной согласованной модели.

## 2. Состояние прохождения

Состояние игрока хранится в одном версионированном JSON-файле в `user://`. Это только компактное сохранение прохождения, а не база всех диалогов, квестов и текстов игры.

Даже при большом объёме авторского текста этот JSON остаётся небольшим: он содержит идентификаторы уже показанных сообщений и изменяемые значения, но не содержит сами тексты и определения ветвлений. В сохранение входят только изменяемые данные:

- версия формата сохранения;
- текущая сюжетная секция и флаги мира;
- состояния квестов;
- последовательность открытых сообщений отдельно для каждого NPC;
- выбранные варианты ответа;
- прочитанные и непрочитанные сообщения;
- инвентарь игрока и NPC;
- снабженческие кредиты и другие ресурсы;
- приобретённые пассивные перки;
- открытые точки карты;
- текущая или последняя выбранная точка вылета;
- краткие результаты завершённых торговых операций и улучшений для журнала.

Координаты произвольной точки карты сохраняются как отдельные числа `x` и `y` либо как массив чисел. JSON Godot не поддерживает `Vector2` напрямую.

## 3. История персональных диалогов

Сохранение не дублирует полный текст всех реплик. Для каждого контакта оно хранит упорядоченный список записей журнала:

- идентификатор сообщения;
- порядковый номер;
- состояние прочтения;
- выбранный вариант, если он был;
- переменные сообщения, если текст зависит от числа или названия предмета;
- снимок результата для торговли или улучшения.

При загрузке статический текст восстанавливается из авторского контента по идентификатору, а индивидуальный результат — из сохранённых параметров.

## 4. Настройки игрока

Громкость, язык, управление и графические параметры хранятся отдельно в `user://settings.cfg` через `ConfigFile`.

Настройки не смешиваются с прогрессом демо и могут пережить удаление или перезапуск сохранения.

## 5. Web/HTML5

В Web-экспорте Godot отображает `user://` на браузерное хранилище IndexedDB. Игровой код продолжает работать через обычные `FileAccess` и `ConfigFile`; прямой доступ к JavaScript `localStorage` не нужен.

Ограничения браузера:

- пользователь должен разрешать браузерное хранилище;
- приватный режим не гарантирует сохранение между сессиями;
- браузер может удалить локальные данные при нехватке места или длительном отсутствии игрока;
- в `iframe` персистентность может зависеть от политики сторонних данных;
- игра должна проверять `OS.is_userfs_persistent()` и предупреждать, если надёжное сохранение недоступно.

Автосохранение выполняется после каждого значимого изменения:

- выбора в диалоге;
- принятия или сдачи квеста;
- торговли;
- покупки перка;
- выбора точки вылета;
- возвращения в ХАБ;
- перехода между сюжетными секциями.

## 6. Что не использовать в демо

- SQLite: лишняя сложность, особенно для Web-сборки и расширений.
- Прямой `localStorage`: создаёт отдельный веб-специфичный путь сохранения.
- Полную сериализацию дерева сцен: сохранение должно отражать состояние игры, а не внутреннее устройство текущей сцены.
- Полные копии текстов диалогов в сохранении: это усложняет исправления и локализацию.
- `ConfigFile` для всего прогресса: он подходит для настроек, но не для вложенной истории диалогов и квестов.

## Итоговый набор технологий

| Назначение | Технология |
| --- | --- |
| Авторский игровой контент | Custom Resources (`.tres`) в `res://` |
| Прогресс, диалоги, квесты, инвентарь | Версионированный JSON через `FileAccess` в `user://` |
| Настройки | `ConfigFile` в `user://` |
| Физическое хранение в Web | IndexedDB, прозрачно через `user://` |

Подробная модель разбиения диалогов и ветвления описана в «04 — Модель диалогов и квестов».
